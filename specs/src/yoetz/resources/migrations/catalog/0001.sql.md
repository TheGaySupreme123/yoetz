## Purpose

This future file is the wheel-installed copy of the reviewed catalog migration. It lets an
installed `yoetz` initialize a catalog without a source checkout. It deliberately contains no
generated environment values and must be byte-identical to `migrations/catalog/0001.sql`.

## Public surface

The resource is addressed by logical name `migrations/catalog/0001.sql`. Its bytes, size, SHA-256,
media type `application/sql`, migration family/version, and destination path appear in the resource
manifest. It is read through package-resource APIs, never by constructing a checkout-relative path.

## Behavior

The build synchronization step copies the canonical source bytes without newline conversion,
templating, comment injection, minification, timestamp stamping, or platform normalization. The
installed migration loader:

1. resolves this logical resource inside the installed distribution;
2. reads bytes once with a configured small resource cap;
3. verifies size and SHA-256 against the installed manifest before UTF-8 decoding;
4. rejects BOM, non-LF line endings, missing final LF, and manifest/path disagreement;
5. supplies the exact decoded SQL to the catalog migration registry.

The complete schema behavior, statement ordering, constraints, and failure contract are defined in
`specs/migrations/catalog/0001.sql.md` and are part of this file's contract by exact byte equality.
The package copy never becomes an independently editable source.

This equality specifically includes the `task_routes.route_generation` and
`active_route_identity_digest` columns, catalog-scoped `maintenance_operations` state machine,
privacy policy history/transitions, three-branch privacy audit/local-consume/receipt-query state,
catalog live-root sets, one-pending-operation indexes, and `retained_task_routes` recovery/CAS
records. A packaged catalog
migration without those objects cannot run the maintenance adapter and is rejected as a schema/
resource mismatch; runtime never creates them ad hoc.

Builds fail when source and embedded bytes differ. Runtime failure occurs before any catalog DDL
when the installed byte digest differs. The loader does not fetch a replacement, use the root
checkout, accept an override search path, or repair the wheel in place.

## Errors and edge cases

- Missing, duplicate, unreadable, oversized, or digest-mismatched resource rejects initialization
  with a bounded package/resource integrity code.
- Zip/wheel resource traversal uses the standard resource abstraction; code must not require the
  resource to be a persistent filesystem path.
- A case-insensitive filesystem collision is detected by manifest verification at build time.
- Diagnostics identify the logical resource ID and expected/observed digest prefixes only; they do
  not expose installation paths or SQL text.
- Editable installs are held to the same parity rule as wheels.

## Invariants

1. Embedded bytes equal reviewed source bytes exactly.
2. Manifest verification precedes execution.
3. No runtime download or dynamic SQL generation can replace this file.
4. A released digest remains addressable in release evidence and old-bundle fixtures.
