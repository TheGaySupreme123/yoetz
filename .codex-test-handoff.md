**Prepared:** 2026-07-24, expanded after independent repository, runtime, and history review.
**Decision:** **do not merge or release the experiment.** It demonstrates better cooperative Yoetz recording, not working multi-provider semantic dispatch and not a successful verification receipt.

## Executive assessment

| Question | Result | Evidence and meaning |
| --- | --- | --- |
| Did Codex use Yoetz? | **Yes** | It called start, status, publish_work, and check. Valid publications advanced the task frontier to 10. |
| Did Yoetz issue a completion verdict or receipt? | **No** | Every observed check returned public INTERNAL_ERROR; no check, finding, or receipt resulted for the task. |
| Did the code deliver working endpoints for Anthropic, Gemini, OpenRouter, and Vercel AI Gateway? | **No** | It implements setup/binding presets only. New IDs are not selected by runtime factory composition, and tests do not perform live protocol/endpoint dispatch. |
| Was the narrow implementation candid about its limit? | **Mostly yes** | Issue #15 was opened, owning specs were updated, and no PR was opened while egress acknowledgement awaited. |

**Bottom line:** Yoetz records cooperative work materially better than the July 22 dogfoods, but check cannot yet gate completion. A durable frontier is workflow telemetry, not approval of a code change.

## Evidence rules and scope

Conclusions follow this authority order:

1. ADRs and owning specs define allowed behavior and public claims.
2. Git objects establish exact source snapshots.
3. Raw Codex JSONL and Yoetz health probes establish what happened in the run.
4. Tests establish only the behavior that they execute.
5. The postmortem and this handoff are synthesis, not product authority.

Do not infer full operation from a successful lower layer:

- MCP registration does not prove observation, advice, semantic dispatch, or receipts are composed.
- A saved provider preset does not prove a provider can be reached, authorized, or parsed safely.
- A publish_work frontier does not prove a diff was reviewed or checked.
- A recorded CLI/model version is not a current-installation claim.

## Architecture and trust-boundary check

The experiment must satisfy the existing authority chain:

1. ADR-006 permits no direct provider path. An immutable approved case must pass classification, policy, minimization, secret scan, authorization, gateway, and privacy audit before a provider adapter sees it.
2. ADR-009 makes egress consent, minimization, independent channels, and receipts part of the contract.
3. ADR-014 limits owner-declared OpenAI Responses endpoints to exact service-TOML https_origin values; it is not a generic OpenAI-compatible escape hatch.
4. INTERFACES.md and owning CLI/config specs define public vocabulary and data boundaries. Docs cannot make an uncomposed runtime release-ready.

~~~text
CLI/MCP request
  -> task state and deterministic checks
  -> classify + minimize + redact + secret scan
  -> approved policy / durable authorization
  -> privacy gateway
  -> exact capability-tested provider profile
  -> bounded parsed judgment or explicit coverage gap
  -> durable receipt, findings, and status/next action
~~~

The experiment reaches primarily **configuration selection**. It does not prove the path from advertised preset to runtime factory, approved outbound case, capability fixture, or closed receipt.

## Observation/advice boundary: what this run did and did not exercise

The current observation/advice runtime is more substantial than simple MCP registration, but the July 24 provider-presets run did not prove its end-to-end use:

| Layer | Current implementation boundary | Evidence in this run |
| --- | --- | --- |
| Local service | The trusted service owns vault keys, decrypted state, writers, provider gateway, and application facade. CLI, MCP, agents, and providers are bounded clients. | Service was ready during the historical health probe. |
| Observation control | ingest, status, pause, resume, and revoke are **local-control** methods. They are deliberately not additional MCP tools. | Not demonstrated; workspace observation/hook consent was absent. |
| Durable observation | ObservationCoordinator validates session/workspace binding, captures/redacts allowed content, persists it, materializes work, queues verification, and recomputes advice. LocalObservationStore holds private local state; SqliteObservationStore is the durable mapped-task store. | Not demonstrated by the explicit provider-setup task. |
| Advice/status | Ordinary status with view=advice is session-aware; it uses session-scoped advice when the migration-0004 route exists, then a workspace fallback. | Not demonstrated. No advice snapshot should be inferred from an MCP status call alone. |
| Verification | ObservationVerificationSupervisor is wired into ready composition; optional wiring can fall back to inline verification. | Not demonstrated; do not assert which optional route was active. |

Observation consent is independent of egress consent. The local store is intended to retain allowlisted structural state and commitments, not raw workspace paths or transcript prose. A hook_observed claim requires real observation evidence with an active lifecycle; trigger-only or degraded sources do not qualify.

This matters because the run shows **explicit cooperative MCP publication**, not an MCP-exposed observation system. Do not describe it as a seventh MCP tool, a global “latest advice” proof, or hook-driven Codex steering.

### Current runtime depth, verified separately

The observation stack is not merely aspirational: an independent code-path review traced it from Codex session JSONL through coordinator, private local state, durable SQLite state, verification jobs, advice snapshots, and ordinary status. Its targeted observation slice passed **62 tests in 0.84s** on current main.

| Subsystem | Proven by the current code/tests | Still not proven by this dogfood |
| --- | --- | --- |
| Codex import/lifecycle | Safe JSONL locator resolution, conservative structural envelope mapping, private Codex-to-Yoetz session mapping, and non-destructive MCP registration classification. Unknown shapes become gaps rather than inferred success. | That this particular session had active observation lifecycle or valid mapped stream ingestion. |
| State/durability | Local store tracks consent, bindings, cursor/dedup, envelopes, outbox, quarantine, and advice suppression; SQLite is the durable authority for mapped task state, content manifests, session advice, history, and verification records. | That this task reached those durable observation tables. |
| Verification/advice | Generation-fenced jobs, lease recovery, stale-result handling, advice suppression/minimization, health states, and session advice isolation have unit/integration/production-composition coverage. | That a check result or semantic advice changed Codex's code in this run. |
| Safety/fail-closed behavior | Unmapped session yields mapping_missing; policy drift or unreadable approved-check configuration fails closed; verification only queues supported event kinds. | Root cause of the unrelated public check INTERNAL_ERROR. |

Bounded retention is intentional: LocalObservationStore can discard oldest envelopes once its serialized state cap is exceeded, and its dedup cache is bounded. SQLite status is coarser than local health, and session-specific advice isolation requires migration 0004; absent that route the reader falls back to workspace advice. These are implementation constraints, not evidence of failure in the July 24 run.

### 3. Diagnose check before another dogfood claim

1. Extract every check request ID and correlation ID from exec JSONL.
2. Inspect matching service diagnostics with the vault unlocked; preserve only bounded/redacted facts in an issue.
3. Reproduce the smallest valid check request through service and MCP bridge.
4. Add a regression asserting a valid closed check/receipt or a specific safe public error — never silent success or invented clean verdict.
5. Re-run an ordinary Codex task and compare raw calls, ledger, status, verdict, and receipt.

### 4. Pass provider/egress gate before a PR

Obtain and record maintainer acknowledgement on issue #15 for exact provider/profile scope. Then supply direct evidence for:

- a closed, versioned provider-profile registry and exact protocol selection;
- durable endpoint identity, not Python-only UI metadata;
- vault-only credential ingress and fresh dispatch-bound handles;
- capability fixtures for each advertised provider/model/endpoint tuple;
- gateway/policy/minimization/secret-scan coverage for every real outbound request;
- structured parsing, failure/timeout handling, and explicit incomplete coverage;
- closed egress receipts and an installed-wheel end-to-end smoke test.

Do not use generic OpenAI-compatible wording to evade exact-profile and capability-evidence requirements.
